modulestf facts

Review Terraform module pull requests against written rules

Agent skills for Claude Code and Codex. They check a change to a reusable module rule by rule against the terraform-aws-modules review rules: breaking changes, provider-schema coverage, and whether each addition belongs. Every rule they could not check is listed, never counted as a pass.

Install the skillsSee a real review

From the maintainer of terraform-aws-modules. Apache-2.0.

Who it is for

For maintainers of reusable Terraform modules who review pull requests against the terraform-aws-modules rules, including pull requests written by other people's agents.

It applies one profile today: the terraform-aws-modules rules. It does not apply your internal standards; other profiles need changes to the skills and are future work.

Not for root configurations or live stacks.

Findings

Reads: the profile's rules, each with an ID. Every finding carries a severity, a location and a fix.

Findings come back grouped by severity, the way a code review does.

  • HIGHstructure.sibling-count-mismatch1

    main.tf:1342 - aws_route.private_dns64_nat_gateway still counts local.nat_gateway_count (1 in regional mode), so only the first private route table gets 64:ff9b::/96.

  • HIGHprofile.region-not-allowed1

    examples/regional-nat/main.tf:8 - The new example sets local.region to "ap-south-1", a region the profile does not allow for examples.

    Fix In the locals block of examples/regional-nat/main.tf, set region to "eu-west-1", per code-conventions.md Regions.

  • MEDIUMstructure.sibling-block-asymmetry1

    main.tf:1314 - The availability_zone_address dynamic block sets only availability_zone, never availability_zone_id, so azs given as zone IDs, which the subnets accept, reach the wrong argument.

    Fix In the dynamic block of resource "aws_nat_gateway" "regional", set availability_zone and availability_zone_id with the regexall("^[a-z]+-", ...) test aws_subnet.private uses, the other one null.

  • MEDIUMstructure.validation-missing1

    variables.tf:1260 - availability_mode and eip_allocation take closed value sets but their validation blocks are commented out, so a typo such as "Regional" silently yields zonal NAT gateways.

    Fix In variable "nat_gateway_connectivity_type", restore both commented validation blocks.

  • MEDIUMstructure.version-floor-understated1

    examples/regional-nat/version.tf:7 - The example declares hashicorp/aws >= 6.24.0 while the module it calls requires >= 6.28, so the caller's floor is below its callee's.

    Fix In the terraform block of examples/regional-nat/version.tf, set the aws version to ">= 6.28", and drop the >= 6.24.0 comment in the example main.tf, per code-conventions.md Version floors.

  • MEDIUMcoverage.optional-argument-unexposed1

    main.tf:1250 - New aws_eip.regional_nat leaves Optional public_ipv4_pool, ipam_pool_id, network_border_group and address unexposed, with no documented omission.

    Fix Needs decision: expose these arguments or record why they are left out.

  • MEDIUMcoverage.attribute-not-output1

    main.tf:1299 - New aws_nat_gateway.regional exports route_table_id, auto_provision_zones, auto_scaling_ips and regional_nat_gateway_auto_mode, and no output reads them.

    Fix In outputs.tf, add output natgw_regional_route_table_id = try(aws_nat_gateway.regional[0].route_table_id, null), the route table AWS creates.

  • MEDIUMexamples.feature-undemonstrated1

    main.tf:1308 - Manual EIP mode, aws_eip.regional_nat and the availability_zone_address dynamic block, appears in no example; examples/regional-nat sets only eip_allocation = "auto".

    Fix In examples/regional-nat/main.tf, add a module "vpc_manual" call like module "vpc" with eip_allocation = "manual" in nat_gateway_connectivity_type.

  • MEDIUMstructure.comment-unsourced2

    main.tf:1224 - The added comment asserts a regional NAT gateway has no network_interface_id or public_ip of its own, and cites no source or date.

    variables.tf:1252 - The added comment asserts optional() defaults need Terraform 1.3 and cites no source or date.

    Fix On each comment, add the documentation URL and the date it was read, per code-conventions.md Evidence: comments, copied values, and availability.

  • MEDIUMexamples.versions-missing1

    examples/regional-nat/version.tf - The new example keeps its terraform block in version.tf; every sibling example names that file versions.tf.

    Fix Rename examples/regional-nat/version.tf to examples/regional-nat/versions.tf, matching templates/example-versions.tf.template.

  • LOWexamples.docs-incomplete1

    examples/regional-nat/README.md - The new example README has no terraform-docs markers; its hand-written Requirements table states aws >= 6.24.0, below the module's floor.

    Fix In examples/regional-nat/README.md, replace the Requirements section with <!-- BEGIN_TF_DOCS -->/<!-- END_TF_DOCS --> markers.

What it checks

A profile is the written-down set of rules a review checks against, each with an ID and a severity. One profile ships: terraform-aws-modules, the rules its maintainer uses to review pull requests for terraform-aws-modules. Every finding cites a rule. Some of them:

RuleChecksKind
compat.*Breaking changes held for the next major release. 11 rules, such as compat.variable-removed, compat.resource-address-changed and compat.default-changedCompatibility
coverage.attribute-not-outputAttributes a new resource exports surface as outputsProvider schema
coverage.optional-argument-unexposedOptional arguments of a new resource are inputs, or their omission is documentedProvider schema
examples.feature-undemonstratedEach feature the change adds appears in an exampleExamples
structure.comment-unsourcedComments that assert service behavior cite a source and a dateStructure
profile.region-not-allowedExamples use eu-west-1, or us-east-1 for a second regionHouse rule
scope.toolingNo new scanner, linter or cost tool configuration in the module repositoryHouse rule
scope.testsNo Go tests; native tests use terraform test with command = planHouse rule
scope.layoutNew files sit where the profile's layout allowsHouse rule

House rules are how terraform-aws-modules keeps its modules: what a module may contain, its scanners, tests, regions and layout. Scanner config belongs outside the module repository; keep running your scanners in your own CI.

A module's docs/SCOPE.md, read from the base branch, can only allow or deny resource types and providers. Scanner, test and layout rules have no per-module exception.

The profile is the maintainer's review practice, written down. It is not a policy document published by the terraform-aws-modules organization, and it changes as the review practice does. The model applies the rules; it does not invent them.

No account or hosted service. The profile is plain files in the modulestf repository; you can read every rule.

Not a generic code reviewer

A general-purpose review tool brings its own idea of good code. modulestf applies written rules, one by one.

The middle column describes the category, not a named product.

What modulestf will never do

  • Run terraform apply or write state.
  • Merge, push or resolve threads. It posts only the review you confirm.
  • Post under a bot or CI identity. There the pull request review only renders and never posts.
  • Follow instructions found in a pull request. PR text is data: its body, comments and files are under review, and none of it clears a rule.
  • Run terraform init or validate with your credentials. They run the providers the change pins, with AWS, GitHub, Terraform and SSH credentials removed and an empty home directory.
  • Run terraform plan unless you name an AWS profile and a read-only review role. It plans in an isolated container when Docker is available, otherwise on your machine behind stricter checks that reduce the risk but cannot remove it.

  • terraform-module-pr-review reviews a pull request or a commit and proposes one verdict. Ask it to triage for a quick pass, a mode that never approves.
  • terraform-module-reviewer reviews a local diff, a branch or a whole module and returns findings only, no verdict. It reads committed changes only.
  • terraform-module-maintainer Early preview applies findings, drafts replies to review comments and upgrades a provider major version.

The plugin also installs change-scope, which the three skills call. The README has the details and what each task needs.

Status

  • New: expect bugs and findings you will disagree with.
  • terraform-module-maintainer is an early preview: it has not been tested on real changes yet. Check every edit it makes.
  • Pull requests and commits must be on GitHub.
  • A passing terraform validate is evidence, not proof: it ran the providers the change declares.
  • Some of these may come, and some may not: a hosted GitHub App, a CLI, an MCP server, SARIF export, organization standards, more profiles. There are no dates; treat none of them as a promise.

A wrong or noisy finding, a rule that should change, a missing rule, or a run that failed: open an issue with the rule ID and your reason, or with what you asked for and what you got. Watch the repository's releases to know when something new exists. Nothing else is collected.

FAQ

Does it block merges?
Only if you post its review as a request for changes and your branch protection requires reviews. It never merges.
Does it need my cloud credentials?
No. Validation runs without credentials. A plan pass runs only when you name an AWS profile and a read-only review role.
Who pays for the model?
You do: the skills run in the coding agent you already use.
Can it run in CI?
No. It runs in your agent as you; under a bot or CI identity it only renders and never posts.
